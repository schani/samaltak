# Lowtalk: the VM in Smalltalk

The VM (object memory, GC, interpreter, scheduler, primitives, image I/O) and the platform layer are written in *Lowtalk*, a subset of Smalltalk that is also plain Smalltalk:

- **Running it directly is the simulator.** Lowtalk classes are ordinary classes in the image. A `VMSimulation` instantiates the modules over a `SimulatedMemory` and runs them, so the VM can be stepped in the debugger, profiled and tested without a C compiler.
- **`VMTranslator` turns it into C** (`vm/gen/`, checked in). The C build compiles only generated code.

**Smalltalk in Smalltalk.** The VM Simulator tool (World menu) boots a guest image on the simulated VM. No separate program runs: `VMMain` is ordinary Smalltalk, in a Process of this image, and the status line says so ("the VM's own Smalltalk classes, in this image"). Run boots the mini kernel (`vm/tests/mini`, built at each Run in 0.2 s) running `MiniTests>>testGuest`, a line a second with `Smalltalk vmBanner` (`VMMain>>banner`) in the output pane; the first line appears within a second. Edit `VMMain>>banner` in the System Browser, ⌘S, and the next line shows it: the guest's VM is these classes. The status also shows the bytecodes simulated and their rate (about 200k/s). Its Smalltalk-80 button boots `st80/` instead, and once it opens the guest display the window shows only the toolbar and that display (at 2 points a pixel when the screen leaves room; the guest's Transcript shows its output): this image's own Kernel and Compiler packages (links into `src/`) and a small UI (`ST80-UI`: the grey desk, windows with title tabs, a Workspace whose cmd-P compiles with the guest's Compiler, the Transcript, a bouncing ball titled `VMMain>>banner`) on the VM's guest display primitives (`DisplayPrimitives`: a 1-bit screen, X11's misc-fixed 7x14 bitmap font, input). Only a simulated VM has a guest display: `GuestDisplay`'s method bodies draw into the tool's screen pane (`VMSimulation>>display:`, a GuestScreen), and in C every call fails. Built at each Run (host `--jit baseline` 0.3 s, `opt` 0.7 s, `none` 1.1 s), it draws its first frame 0.3–1.1 s later; the animation costs 280 bytecodes (0.5–1.5 ms) a frame, a key is on the screen within 12 ms (the guest polls every 10 ms), a print-it of `3 + 4` within 25, 40 or 75 ms. The guest's Process runs below the windows (priority 30, about 1% of a core): a visible World keeps presenting at 60 fps (a hidden one presents only on change, so its frame counter reads low). World menu › Rebuild VM & reboot (or the tool's button) does it to the image itself (`VMRebuilder`): `VMTranslator generateVMInto: <dir>/gen`, `nice make BRIEF=1` with `vm/Makefile` into `<dir>/build/samaltak` (output streamed into its window, ~3 s), a rename to `<dir>/samaltak` (a running binary keeps its file), `Smalltalk snapshot:`, then `File primExec:` of that binary on the image with the image's arguments, `--control-port` pinned to the port in use. `<dir>` is `build/vm` beside the source directory (`--source-dir`), never `vm/gen`. The exec keeps the pid, standard streams and control port, so a samaltak-ctl session carries on (its requests retry while the pid lives and the port refuses); the image resumes as from any snapshot (windows, a running guest), now showing the new banner in its top bar. The simulated clock never goes back, so a guest survives its host's restart.

Packages (all layer 0): `VM-Lowtalk` (the language's runtime: `VMModule`, `VMStruct`, `CLibrary`, `CPointer`, `SimulatedMemory`, `VMSimulation`), `VM-Translator`, `VM-Core` and `VM-Platform` (the VM), `VM-Jit` (machine code, see docs/jit.md), `Tests-VM`.

## Rules

Everything below means the same in Smalltalk and in C; anything else is rejected by the translator.

**Modules.** A `VMModule` subclass is a C module (one `.c` file). Its instance variables are C globals, its methods C functions. `declarations` (class side) answers `#((name type [initialValue]) ...)`; variables typed with a module or library class (`(memory ObjectMemory)`) connect modules and produce no C. Abstract module classes (`isAbstractModule`) may only declare connections; their methods are shared helpers. A module's class-side `cPreamble` goes at the top of its C file (before the header). Calls go to `self` or to a connection: `memory allocObj: cls format: F_FIXED slots: 3`. An *interface* (`isInterface`, e.g. `PlatformInterface`) only declares functions; a subclass implements them (one selector, one C function, one signature), and the build links one implementation.

**Operating systems.** A module or C library whose class-side `targetOS` is `#darwin` or `#linux` is for that OS only: its headers, prototypes and C file are guarded by `__APPLE__` or `__linux__`, and `sources.mk` lists its file under the OS (`VM_CORE_SOURCES_LINUX`, ...), which the build adds by `uname -s`. So what differs between operating systems is an interface with one implementation per OS (`Ticker`: `KqueueTicker`, `TimerfdTicker`; `JitPlatform`; `PlatformHost`), and one `vm/gen` serves both. A module for every OS may not use one OS's library or module (the translator rejects it). A simulation connects an implementation that `isSimulated` (the Darwin ones: their libraries are simulated). Plain spelling differences of a C API stay in a library's `headers`, which may contain preprocessor lines (`'#ifdef __APPLE__' '<util.h>' '#else' '<pty.h>' '#endif'`).

**An OS without a C library** (`#uefi`, docs/uefi.md) has a translation of its own, not in `vm/gen`: `VMTranslator generateVMInto:os:arch:` takes the VM's modules for every OS and those for that OS. A module for it whose class-side `replaces` names a C library or a module (or an Array of them) takes its place: calls to it are sends to the module, under the same selectors, and a replaced module is not translated (`UefiLibC` replaces `LibC`, `UefiNoDisplay` `PlatformWindows`). A replaced library's names are free (`UefiLibC>>memcpy:from:size:` is C's `memcpy`, which the compiler calls too); its variadic functions are inline methods taking their arguments as 64-bit words (`self varargBits: x`: a double's bits, an integer widened, a pointer's address). An interface implemented for the OS is implemented by that module alone (`UefiPlatform`, not `SDLPlatform` or `HeadlessPlatform`). Only the headers of the libraries the translation calls are included, and only the structs its code names; `definedExternStructs` names the ExternStructs the translation defines.

**CPUs.** The same for the CPU: a module whose class-side `targetArch` is `#arm64` or `#x86_64` is for that CPU only (`sources.mk` lists it under `VM_CORE_SOURCES_ARM64` or `_X86_64`; the build adds those of its `uname -m`, arm64's on any CPU but x86-64). A module for every CPU reaches one for a CPU through an *arch interface* (`isArchInterface`: `JitAssembler`; `ByteBlocks`: the string search primitives' 16 bytes at once with SSE2 on x86-64, 8 in a 64-bit word elsewhere): in the translation for a CPU a connection typed with it is its subclass for that CPU, whose inline methods expand there; a method marked `<arch: #x86_64>` exists only in that CPU's translation, and a condition that folds per CPU (`asm isX64 ifTrue: [...] ifFalse: [...]`) translates only its branch. Where any of this differs, `translate` translates once per CPU and `TArchMerge` merges: a function that differs is there twice, `#if defined(__x86_64__)` its x86-64 translation `#else` arm64's `#endif`, as is what differs in the header and between functions; a file for one CPU is guarded. Each CPU's compiler sees exactly its own translation (arm64's is the C the VM had before it had a second CPU). `VMTranslator generateVMInto:for:` translates for one CPU only (the VM Rebuilder's: half the time).

**Constants** are class variables in UPPER_SNAKE case (`F_BYTES`, `CTX_SENDER`), shared through `VMConstants` (the image's single definition of the object model) or private to a module; set in the class-side `initialize`. They become `#define`s. A module sees its own and its superclasses' constants; another hierarchy's it gets through inline accessors of a connection (`runtime prologueBytes`), which fold to the constant (docs/jit.md, Constants).

**Functions.** A method marked `<function>` is a C function; so is one marked `<export>` (non-static even if no Lowtalk module calls it) or `<noreturn>` (never returns), a primitive, and every method of an interface. Any other method is inline: expanded at each call, untyped and generic, blocks passed to it inlined too. A function's C name is its selector's first keyword in snake case (`allocObj:format:slots:` → `alloc_obj`); if another function or a C library function, global, local or type has that name, it takes its module's name in front (`interpreter_widow`), and if that still clashes (two selectors, one first keyword) its whole selector. Its signature is inferred: a parameter's type is the join of the types of the arguments at all its call sites, its return type the join of the types of its `^expression`s (`void` if there is no `^` with a value). A literal or named constant adapts to the values it joins with (alone: its own type, `int` for small integers); integers join to the narrowest type that holds both (none for an `int64_t` and a `uint64_t`: cast one), a pointer and a `void *` to the pointer type, unrelated pointers to `void *`. Functions called through one function pointer (`self functionPointer: #name:`, `fn call: x`) share a signature; a C library parameter, a struct field or a typedef it goes to fixes it. Where nothing tells the type (a function only called from machine code or from C) or the join is not what is wanted (a literal-only parameter that must be wider, a result wider or narrower than its expressions), `<var: #name type: 'T'>` declares a parameter and `<returns: 'T'>` the return type. `const` in types is kept in the C but not checked by the translator (the C compiler checks it). Local variable types are inferred from the first assignment (an integer literal gives `int64_t`); `<var: #name type: 'T'>` declares one. A local assigned exactly once, with a constant, is that constant (no variable), so case analysis on it folds away.

**Integers** are mathematical in Smalltalk and fixed-width in C, so:
- a value must fit its type; wrapping is explicit: `asUInt64`, `asInt64`, `asUInt32`, `asInt32`, `asUInt16`, `asInt16`, `asUInt8`, `asInt8` (C casts);
- implicit conversions may not lose values (assign a `size_t` to an `int32_t` local: write `asInt32`); stores into memory (fields, `at:put:`) may narrow, the simulator checks each stored value;
- comparisons, `quo:`, `rem:` and `>>` may not mix signedness where C would convert a possibly negative operand to unsigned; `+ - *` and bit operations may (the result is the same modulo 2^64);
- `<<` only on 64-bit values (`asInt64`/`asUInt64` first): narrower shifts overflow in C, not in the simulator;
- an unsigned `to:` limit may not be computed by a subtraction (it wraps in C when it would go negative);
- `quo:`/`rem:` (truncating) only; `/` only on doubles; no `//`, `\\`;
- `<<`, `>>`, `bitAnd:`, `bitOr:`, `bitXor:`, `bitClear:`; `bitInvert` only on signed values (`bitInvert64`/`bitInvert32` for unsigned);
- overflow checks: `x ifNoOverflowAdd: y do: [:r | ...]` (also `Sub`, `Mul`) runs the block with the 64-bit signed result if there was none (`__builtin_*_overflow`);
- 128-bit steps of unsigned 64-bit values: `self mul64: a by: b plus: c plus: d high: h` answers the low 64 bits of a * b + c + d and stores the high ones into `h` (a `self local: 'uint64_t'`), `self div128: hi low: lo by: d remainder: r` answers (hi * 2^64 + lo) quo: d for hi < d and stores the remainder into `r` (`lt_mul64`, `lt_div128`: `unsigned __int128`);
- `$a value` is a character code; `=`/`~=` compare values; `==`, `~~` and `nil` are not Lowtalk.

**Control flow:** `ifTrue:ifFalse:` (conditions must be `bool`), `and:`/`or:`, `whileTrue:`/`whileFalse:`, `to:do:`/`to:by:do:`, `timesRepeat:`, `repeat`, `caseOf:otherwise:` (a C `switch` for constant keys), `^`. Blocks only as arguments of these or of inline methods.

**Pointers** (`T *`): `p at: i`, `p at: i put: v`, `p value`, `p value: v`, `p + n`, `p - n`, `p - q`, comparisons, `p isNull`, `p notNull`, `self null`. A struct pointer answers its fields (`fr method`, `fr method: m`), `p fieldAddress: #method` (`&p->method`), `p copyStructFrom: q` (`*p = *q`); `p at: i` of a struct pointer is `p + i`. Casts: `self cCoerce: e to: 'T'`. Raw memory: `self uint64At: a`, `self uint64At: a put: v` (also `uint32`, `uint16`, `uint8`, `int*`, `float64`, `float32`). `self sizeof: 'T'`. Function pointers: `self functionPointer: #ticker:`, called with `fp call`, `fp call: x`, ... (up to ten arguments). A calling convention is part of a function type, `'uint64_t (__attribute__((ms_abi)) *)(uint64_t)'`, and `<abi: 'ms_abi'>` gives a function one (UEFI's on x86-64); a function whose pointer goes where such a type is expected takes it. An address cast to a function pointer type (`(self cCoerce: entry to: 'int64_t (*)(int64_t)') call: 42`) calls machine code, which the simulator does not run: it runs the VM without the JIT (docs/jit.md).

**Locals in memory.** `p := self local: 'T'` answers a pointer to fresh zeroed storage for a `T` (a struct, a scalar out-parameter, an array `'char[256]'`), living until the function returns.

**Strings.** A string literal is a `char *` for C library calls and for storing into memory. To read one as bytes, write `self cString: 'literal'`.

**Structs.** A `VMStruct` subclass is a C struct; `fields` (class side) answers `#((name type) ...)` (`(name 'T[n]')` arrays, `(union (a T) (b U))`); field names must not be methods of `VMStruct`. The header checks with `_Static_assert` that C lays a struct out as the simulator does. An `ExternStruct` names a C library struct (`cName`) and the fields the VM uses, by their C names.

**C libraries.** A `CLibrary` subclass declares the C functions, variables and macros the VM calls: `<c: 'void *memcpy(void *dst, const void *src, size_t n)'>` (variadic ones once per arity), `<cVariable: 'FILE *stderr'>`, `<cMacro: 'int PROT_READ'>`, `<noreturn>`; class-side `headers` are included, `typedefs` answers `#((FILE opaque) (pthread_t uintptr_t))`. The method bodies are the simulation.

**The interpreter loop.** `<bytecode: n>`, `<bytecodes: #(first last)>` (a range; single bytecodes and lists take precedence) and `<bytecodeList: #(...)>` mark handler methods; `<bytecodes: #()>` handles unknown bytecodes. `registers` (class side) names variables that are C locals of the interpreter function. Ending a handler (`^self`) dispatches the next bytecode; `^self someLabel` in a handler is a `goto` to a `<label>` method (its arguments become shared locals) or to another handler; `^self dispatch: byte` re-dispatches; `^self inlineHelper` expands the helper so that each of its returns dispatches. `<specialize>` handlers get one copy per bytecode with `self currentBytecode` constant.

**Primitives:** `<vmPrimitive: 1 name: 'intAdd'>` on a `void` method (`<leaf>`: never allocates or switches; `<notTryable>`: not for the debugger's tryPrimitive). The translator emits the table (`primitive_entries.c`); the image compiler and builder read the names and numbers from the same methods.
