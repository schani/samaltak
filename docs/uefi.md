# The VM on UEFI

The VM runs as a UEFI application on x86-64 and arm64, with its UI on the firmware's screen: no operating system, no C library, no hand-written C, no file system. It is translated from the same Lowtalk as `vm/gen`, with the `VM-UEFI` package in place of the C library and the OS. The image is everything there is (sources, fonts) and lives on a raw partition.

    make uefi                                       # $(OUT)/uefi-$(UEFI_ARCH)/esp: a boot volume; .../image.disk: the image
    make uefi-run UEFI_ARGS="--headless --eval '3 + 4'"   # boot it in QEMU with its UEFI firmware; fails unless the VM exits 0
    make uefi-ui                                    # the World in a QEMU window (macOS: UEFI_SCREEN points, in front; needs Accessibility)
    make uefi-control UEFI_CONTROL_PORT=7341        # no window; its control service on 127.0.0.1:7341 (samaltak-ctl open --uefi)
    make test-uefi                                  # the tests that need no platform layer, the World, the network, a snapshot

`UEFI_ARCH` is `x86_64` or `arm64`, this machine's by default. Needs clang, ld.lld, `qemu-system-x86_64` or `qemu-system-aarch64` and the firmware for it, OVMF or AAVMF (`.agents/setup` installs this machine's; Homebrew's `qemu` has both). For this machine's CPU QEMU runs the VM on it, with KVM where `/dev/kvm` is there, else on macOS with Hypervisor.framework (QEMU 11.0 fails at its start on macOS 26; 11.1 works); for another CPU it emulates (TCG), and the VM still boots in about 5 s.

`make uefi-control` forwards the guest's listener to host loopback. Direct boots with `--control` and no supplied token require firmware `GetRNG`; without it the control service does not listen. The auto-generated token is announced on the console. `tools/samaltak-ctl open --uefi` instead provides its own random token in private guest boot arguments. See [remote control authentication](remote-auth.md) before enabling the service on real hardware.

## How

- **Translation.** `VMTranslator generateVMInto: dir os: #uefi arch: #x86_64` (or `#arm64`) translates the core's modules for every OS and `VM-UEFI`'s (docs/lowtalk.md, An OS without a C library): `UefiLibC`, `UefiLibM` and `UefiPosix` implement `LibC`, `LibM` and `Posix`; `UefiTicker`, `UefiJitPlatform` and `UefiPlatform` the core's `Ticker`, `JitPlatform` and `PlatformInterface`. The platform primitives are `PlatformPrimitives` as everywhere, over VM-UEFI's modules in place of the SDL and POSIX ones: `UefiMachine` (the firmware for the machine primitives), `UefiSnp` (the raw network interface), `UefiNoDisplay` for windows, events, the refresh and the GPU, and `UefiNoIO` for files, sockets, TLS and ptys, which all fail; the raster primitives are `PlatformRaster`'s, as everywhere. What differs between the CPUs is `UefiCpu`, an arch interface (`UefiX64Cpu`, `UefiArm64Cpu`): the cycle counter, instruction cache maintenance, switching stacks, with the instructions C has no builtin for in their C preambles. Not checked in: `make uefi` translates into `$(OUT)/uefi-$(UEFI_ARCH)/gen`.
- **Core FFI.** UEFI does not publish FFI wrappers at runtime. Prepared `vm:core` descriptors for float fraction and printing, wall and thread clocks, and stdout/stderr select statically linked typed wrappers. Each call checks the exact name, signature and arguments; no native address or binding token is stored in the image. UEFI has no dynamic grants or environment. Large Integer arithmetic uses the image implementation.
- **Compiling.** `vm/uefi.mk`: clang for `x86_64-unknown-none-elf` or `aarch64-unknown-none-elf`, freestanding, with the ABI the JIT assumes (on x86-64 System V); the firmware's functions are called through `ms_abi` function types (`UefiModule>>efi:with:...`), and `efi_main` and the timer's notification function are `ms_abi` (`<abi: 'ms_abi'>`): UEFI's convention on x86-64, nothing on AArch64, where UEFI's is the standard one. `ld.lld` links a static PIE; `UefiImageWriter` (Smalltalk) turns it into a PE32+ EFI application: one read-write-execute section (the JIT's code cache is the zero-fill array the VM reserves for it) and base relocations.
- **Boot volume.** FAT, as the firmware requires: `EFI/BOOT/BOOTX64.EFI` (`BOOTAA64.EFI`) and `samaltak.args`, the command line, one argument a line (without it: `disk: --headless`).
- **The image on disk.** `UefiImageStore`: a raw partition or disk that starts with its superblock (found among the firmware's block devices), two slots of image. The image path `disk:` reads the newest slot; a snapshot writes the other, flushes, then writes that slot's header with the next sequence number, so a crash while saving leaves the last good image. `UefiImageDisk` (Smalltalk) writes a store with the image in slot 0; `make uefi` extends it to `UEFI_DISK_MB` (512). Slots are half of what follows the first megabyte: the partition must be at least twice the image plus 1 MB.
- **Devices in the image.** The VM has no display, input or network drivers: the image drives them (`System-Devices`, layer 0) through the machine primitives (`Machine`: memory by address, memory outside the heap, firmware calls in its convention, its events signaling Semaphores; docs/platform.md), with the firmware's boot services and protocols (`Firmware`). `GPUPlatform` (Graphics-GPU) chooses its backends when the image starts: where the VM has no firmware the VM's primitives (`GPUPrimitives`), here `FirmwareDisplay` for windows and events and a `SoftwareGPU` on it. All of it is Smalltalk, editable while it runs.
- **Display.** `FirmwareScreen`: the firmware's graphics output (GOP) in its mode of the size the World opens with (`--window-size`; `make uefi-ui` passes `UEFI_SCREEN`, 1024x768), else the mode it booted with (1280×800 on OVMF), drawn straight into its linear framebuffer; one window, the screen, at one pixel a point (`FirmwareDisplay`); the pointer is an arrow drawn over a shadow copy of the frame, moved without a new frame. Once it draws, the firmware's text console is silenced (its OutputString becomes its TestString). `SoftwareGPU` renders in software: the device (handles, textures and buffers in memory outside the heap, passes, command buffers, the swapchain, fences) is Smalltalk; the pixel work is the raster primitives (`PlatformRaster`, the same on every OS): the Renderer's uber-shader (every mode: solid, glyphs, images, halftone, stripes, lines) with row fast paths for axis-aligned quads, premultiplied blending, blits, copies; the swapchain is a BGRA8 back buffer that `submit` presents. It runs no other shader: a `FragmentShader` (ShaderView, the juggler) shows its error. On a software device (`GPUDevice>>isSoftware`) the Compositor composes only when something changed and rests after each frame as long as it took, so that the other Processes keep at least half of the CPU.
- **Input.** Drivers in Processes at priority 75, above the compositor: `FirmwareKeyboard` (the firmware's extended text input, read whenever the firmware signals its key event: a key stroke is keyDown, textInput, keyUp; Alt is cmd as on Linux), `VirtioInput` (a virtio tablet or mouse through the firmware's PCI I/O, its virtqueue (`Virtqueue`) in the device's DMA memory polled every 10 ms, for firmware without a pointer driver: OVMF has none), else `FirmwarePointer` (the firmware's absolute or simple pointer, read when it signals). `InputQueue` makes and queues the events as the VM's queue does elsewhere, with remote control's injected ones (`RemoteInputDevice`); `RefreshClock` signals the compositor's semaphore at 60 Hz.
- **Network.** The image drives the NIC and does TCP/IP. Its drivers (`PciNetworkInterface`, System-Devices) are for QEMU's standard NICs: `E1000eInterface`, the Intel 82574L (e1000e, the default on q35 and `make uefi-run`'s on x86-64), and `VirtioNetInterface`, virtio-net (virtio 1.x over `VirtioPci`, its queues `Virtqueue`s; the default on arm64 `virt` and `make uefi-run`'s there). `NetworkInterface open` starts the first controller among the firmware's PCI devices that one of them supports: it takes it from the firmware's drivers (DisconnectController, the controllers they made first: VirtioNetDxe with MNP and everything over it, iPXE from an option ROM; `make uefi-run` gives QEMU's NICs none), resets it and drives it on its registers in its memory BARs, its rings and buffers in DMA memory from the PCI I/O protocol. No interrupts: the stack's Process takes the frames when it wakes, at least every 10 ms, and a Process of the driver's, just above the idle Process, looks for a frame without pause while frames came or went in the last 20 ms and wakes the stack when one is there. Without a controller the image supports, the VM's NIC: `UefiSnp` (in place of `PlatformNic`: the `nic*` primitives, docs/platform.md) drives it through the firmware's simple network protocol, opened exclusively so that the firmware's own network stack (MNP and everything over it) lets go of it; it moves what the NIC received into a queue at the platform's polls, every millisecond while the image waits for frames, and while frames come and go a wait polls it without pause (the firmware's timer ticks every 10 ms). The socket primitives fail (`UefiNoIO`); `RemoteSocket` uses the image's stack instead (`NetworkStack active`, System-Network), started on first use: Ethernet, ARP (a cache with aging), IPv4 (to the gateway unless for the subnet; fragments dropped; 127/8 loops back), ICMP (it answers ping), UDP, a DHCP client (renewing the lease), a DNS resolver (A records, CNAMEs, the servers DHCP gave), and TCP (`TcpConnection`, RFC 9293: active and passive opens with a backlog, the MSS option, windows both ways (at most 64 KB: no window scaling), out-of-order segments kept until the gap fills, an RTO per RFC 6298 (Karn; at least 200 ms), fast retransmit and NewReno recovery, slow start and congestion avoidance, delayed ACKs, zero-window probes, RSTs only at the exact sequence number (RFC 5961), every closing state, a TIME_WAIT of 2 s), in a Process of its own at priority 55. So ControlServer, `HTTPClient` (no TLS: no HTTPS) and the rest work unchanged. `--control-host 0.0.0.0` lets the control service listen on every address, which `make uefi-control` does in the guest behind QEMU's user network, and forwards the host's `127.0.0.1:UEFI_CONTROL_PORT` to; `samaltak-ctl open --uefi` runs it, and its screenshots come back in the response. Under QEMU's user network without KVM: 1.5 ms from Smalltalk to an echo server on the host and back; 16 MB from the host in about 0.85 s (e1000e) or 1.3 s (virtio-net), to it in about 1.65 s (either; through the firmware's SNP 0.85 s and 1.9 s with iPXE's e1000e driver, 1.4 s and 1.75 s with VirtioNetDxe).
- **Firmware services.** `UefiFirmware` (`efi_main`): first makes its image writable and executable where the firmware protects it by its sections (edk2 on AArch64 maps the one section read-only; `EFI_MEMORY_ATTRIBUTE_PROTOCOL`, which ArmVirtQemu uninstalls, else the CPU architectural protocol's `SetMemoryAttributes`), turns off the boot manager's watchdog, switches to a stack of 8 MB (the firmware's is 128 KB; the JIT's code keeps a native frame per activation), opens the volume, runs `VMMain`, and powers off with the exit status (`samaltak: exit N` on the console). Console output goes to the serial port if there is one, else to `ConOut` (silent once the image draws on the screen). Memory: `malloc` is the firmware's pool, `mmap` its pages (zeroed). Time: the cycle counter (`rdtsc`, `cntvct_el0`), calibrated against `Stall`; the wall clock is `GetTime` at start plus that. Timers: timer events whose notification calls `Scheduler>>tickFired:` (OVMF's timer ticks every 10 ms). Idle: `WaitForEvent` on a timer and the events the image watches (`UefiMachine`), which halts the CPU.

## Limits

- No files from Smalltalk, TLS (so no HTTPS), processes or ptys; no shaders but the Renderer's.
- The network: one NIC (the first the image has a driver for, else the firmware's first Ethernet one), IPv4 only, no IP fragments, multicast or IP options sent; TCP without window scaling, SACK, timestamps or keepalives.
- Software rendering: a typical 1280×800 frame takes about 4 ms natively, 100 ms or more under QEMU without KVM.
- Memory is physical: the heap's reservations (twice `--max-heap` plus the young space) are allocated and zeroed at start. `make uefi-run` passes `--max-heap 256` (`UEFI_HEAP_MB`) and gives QEMU 2 GB.
- One CPU, the firmware's timer resolution, its block device drivers.

## Real hardware

On a USB stick: a FAT32 partition with the contents of `$(OUT)/uefi-$(UEFI_ARCH)/esp`, and a second partition of at least twice the image plus 1 MB with `image.disk` written to its start (`dd`). Boot it on a UEFI PC (or arm64 machine) with Secure Boot off. The pointer needs the firmware's USB mouse driver (most PC firmware has one; OVMF does not). The network needs an Intel 82574L or a virtio-net, else a NIC the firmware (or its option ROM) has a driver for.
