# JIT

Two compilers on a shared runtime: `baseline` (Cog-style) and the optimizing tier `opt`, whose lower tier is baseline code. Both are written in Smalltalk: Lowtalk for code in the VM (translated to C like the rest of it), ordinary Smalltalk for code in the image. No LLVM at run time. Targets: Apple Silicon (M2 Max, arm64, macOS; also Linux on arm64, e.g. Asahi) and x86-64 Linux (x86-64, below). Both beat Pharo 12's Cog JIT on every Are We Fast Yet, micro and real-world benchmark (Comparison, docs/benchmarks.md).

| `--jit` | what |
|---|---|
| `none` | the interpreter (computed goto, PGO) |
| (all) | Contexts married lazily: closures, `thisContext` and exception handling do not flush frames (in the interpreter, for every mode) |
| `baseline` | Cog-style: own assembler (arm64, x86-64), simulated operand stack in registers, machine-code inline caches (monomorphic, polymorphic, megamorphic), inline SmallInteger/Float arithmetic and common primitives |
| `opt` (default) | baseline code plus an optimizing tier in the VM (Lowtalk): SSA IR, inlining from type feedback, closures not made, unboxed Floats, linear-scan register allocation, deoptimization to frames |

Each compiler has ablation flags (`--jit-flags -ic,-arith,...`) so that the effect of each optimization is measured separately.

## Shared runtime

The interpreter's frames are the canonical state. Machine code runs on the same frame records and C-stack slots; at every safepoint (a call out of machine code that may allocate, collect, flush frames, switch processes or run Smalltalk) the values it holds in registers are in their slots and the frame's `pc`/`sp` are valid. Hence:

- the interpreter can resume any frame of compiled code at its bytecode pc, and compiled code can be entered at the pc of a frame the interpreter was running (on-stack replacement at backward jumps, return into a compiled caller);
- GC roots, `materialize_all` (frames into Contexts), the debugger, stack printing and process switches stay as they are;
- deoptimizing baseline code is free; flushing the code cache only needs no machine code on the native stack.

**Frames.** A `Frame` has a `code` field: its method's `JitMethod` (machine code), 0 (none), or 1 to 0xFFFF while the JIT counts it (activations, then backward jumps). Every frame push sets it: from the method cache entry (`K_JIT` entries hold the code or 1, as `JitRuntime` answered when `fillCache` filled them: installing code leaves the caches alone, an activation through an entry that still counts finds the code compiled since, one through baseline code the optimized code the method has by now, `JitRuntime>>best:`), for blocks from the home method's code. Machine code keeps `pc` and `sp` (one 64-bit store) current at safepoints instead of `ip`; the runtime turns them into `ip`, `nframes` and `cstackUsed` (`Interpreter>>syncFrame:`). Operands live in their slots at offsets known at compile time (`BytecodeAnalysis`: the depth before every instruction).

**Native stack.** Machine code calls compiled callees with `blr` and returns with `ret`, so the native stack mirrors the frames entered since the last `jit_enter`, 16 bytes (x29, x30) per activation. `jit_enter(frame, address)` (`JitStubs`, generated at startup) saves the callee-saved registers, sets x19–x22, remembers the native stack pointer, pushes x29/x30 as a prologue would and branches to `address`. Leaving to the interpreter resets the native stack to `jit_enter`'s and returns: `exitSync` (the code stored the frame's pc and sp: the interpreter continues there), `exitPlain` (the runtime made the frames canonical). Returning from the first activation lands in the trampoline, which answers the caller's frame; the runtime continues its machine code if it has some (`JitRuntime>>run:at:`), else the interpreter.

**Registers** (callee-saved, pinned): x19 the frame record, x20 its slots (`fp`, receiver at `fp[-1]`), x21 the receiver, x22 the `JitState` (nil/true/false and the classes inline paths check, refreshed after every GC; the interrupt flag; the frames array; jit_enter's stack pointer; the young space's bounds). x23–x25 hold nil, true and false, x26–x28 baseline code's loop temps or opt's registers; x0–x17 scratch. Code entered by a caller that pushed its frame (the runtime's sends, optimized code calling baseline code) starts with the prologue (`JIT_PROLOGUE_BYTES`: x19 := the next Frame, push x29/x30, load x20, x21); its start is after the prologue.

**Calls into the runtime.** Machine code stores pc and sp, calls a stub (`ldr x16, =function; br x16`, in the code cache so that `bl` reaches it) with the frame in x0; after a safepoint it reloads x21. The runtime answers 0 (continue), 1 (leave: `exitPlain`) or, for a send, the callee's entry (frame pushed; the caller `blr`s it). If frames were flushed or moved (process switch, stack full, `terminateTo:`), or code was invalidated, it answers 1. Sends through the runtime (`OptRuntime>>send:index:site:` for optimized code's calls that no machine code takes, `JitRuntime>>dispatch:frame:argc:`) use the interpreter's inline caches, keyed by the site's code address: frameless sends (^ivar, constants, setters) touch the frame only when an interrupt is pending (they are safepoints, as in the interpreter); leaf primitives and primitives run as in the interpreter; a method with code gets its frame pushed from the cache entry; a method without code is counted (compiled at the threshold) or its frame is pushed and the interpreter runs it; `perform:` sends its selector, the arguments moved down over it as the primitive does, and a selector not understood sends `doesNotUnderstand:` with a Message of it and the arguments, as the interpreter does; a send the runtime cannot complete cleanly (a full stack; a `perform:` whose primitive fails, of a selector not understood or of `perform:`) leaves to the interpreter to execute it again, which it can because nothing happened yet. Special selectors first try the interpreter's fast paths, `value`/`value:` on blocks enter the block's code. Arrays (`0x94`) are runtime calls, closures when eden is full.

**Interpreter hooks.** Activating a method whose cache entry is `K_JIT` (count, compile, enter at start: `JitRuntime>>activated:`), returning or non-locally returning into a frame with code and activating a block whose home has code (continue at `ip`: `resume:`), a backward jump in a frame whose `code` is not 0 (count, compile, on-stack replacement: `backJump:`). Process switches flush all frames, often (the sampler), so returning into or jumping back in a Context whose method has code marries the Context to a new bottom frame, its sender the base, and continues it in machine code (`resumeContext:`, `Interpreter>>thawFor:`); otherwise long-running loops would stay interpreted and every return into them would leave machine code. With `--jit none` they cost a load and a branch on paths that already do work. The bytecode-pc to machine-pc map holds the resumption points: method and block starts, continuations after sends, loop heads, conditional jumps (a `mustBeBoolean` send returns to them).

**Exits.** A compiler may leave to the interpreter at any instruction (`exitSync`): baseline code does for non-local returns, `mustBeBoolean`, stores into immutable objects or into a married Context's fields, and returns from the bottom frame. The interpreter continues the frame and comes back at the next send, return or backward jump.

**Code.** One `MAP_JIT` region (`pthread_jit_write_protect_np`, `sys_icache_invalidate`), bump allocated after the stubs; it takes the place of a zero-fill array in the VM's image (`CodeCache`), near the VM's data, so that `adrp` from the code reaches it (tiering counters, type feedback, eden's top, call caches). A compiled method's header (`JitMethod`) follows its code: the method (a GC root), the compiler, start, the bytecode map, the notes. Methods are found by identity hash (stable across moves) in a 64K open-addressed table; activations are counted per hash. Scavenges update the methods of headers compiled while the method was young (a list); full GCs and become all of them. Literals are in the code: baseline code's literal pool, optimized code's oop pool (GC roots). When the cache (or the table) is full the method stays interpreted and the whole cache is flushed at the next interpreter hook, when no machine code is on the native stack: frames go back to counting, the method caches are flushed. Become of a compiled method kills its code (its frames are interpreted from then on). Method dictionary changes flush the interpreter's caches, which the runtime's sends use. Snapshots flush the frames; machine code is not saved.

**Triggering.** `--jit-threshold N`: activations before a method is compiled (0: the first); `--jit-osr N`: backward jumps in an interpreted frame before its method is compiled and the frame continues in machine code. `--jit-cache MB` (1–128).

**Disassembly.** The machine code of any method can be shown from the image, for either compiler (compiling it if needed, `CompiledMethod>>machineCode`, `machineCodeFor: #baseline`, the System Browser's method menu): every instruction, grouped under the bytecode it implements (with the source line), and commented with what it does (tag check, overflow branch, spill, call into the runtime by name...). Compilers record the comments as they emit (always for a disassembly, for all code with `--jit-flags notes`; a copy compiled for a disassembly is dropped and leaves the feedback alone); `jitCode` answers code, address, bytecode map, notes and stub names; `Arm64Disassembler` or `Amd64Disassembler` (by `Smalltalk vm jitArchitecture`) prints them.

**Statistics** (`vmStats`, `VMStatistics`): methods and bytecodes compiled, microseconds compiling, code bytes, cache flushes, entries into machine code, exits, resumptions, on-stack replacements, methods that could not be compiled.

**Constants.** The code generators (`JitStubs`, the compilers) are `Arm64Module`s, so they name registers and conditions; the runtime and the analysis are `VMCoreModule`s, with the VM's helpers and constants. Neither needs the other's class variables: the generators ask the runtime through inline accessors (`runtime arith`, `runtime prologueBytes`), struct offsets come from the structs (`(self cCoerce: 0 to: 'Frame *') fieldAddress: #fp`).

## Compilers

`JitRuntime>>compile:mode:notes:` analyzes the method (`BytecodeAnalysis>>analyze:`), then has the mode's compiler emit at the assembler's pc; it appends the header, installs it and counts. A new compiler:

- a module subclassing `JitCompiler` (its conventions: prologue, `emitSync:depth:`, stubs, frame and state offsets) with `compile: aMethod` answering whether it emitted every reachable instruction; it records resumption points (`runtime noteResume:at:`);
- its mode in `JitRuntime>>modeNamed:` / `modeName:` and a case in `compile:mode:notes:`; its flags in `flagNamed:length:` (queried as inline accessors);
- if it keeps values in registers, spills before every runtime call and at every resumption point.

**Baseline** (`JitBaselineCompiler`, `JitBaselineRuntime`, `--jit baseline`). After Cog's StackToRegisterMappingCogit: one pass over the bytecodes with a simulated operand stack whose entries are in their slot, in a register (x0–x8, x12–x15), a constant, nil/true/false (pinned in x23–x25), self (x21), a temp or a literal not loaded yet, or an unboxed Float (d8–d15). Values go from producer to consumer in registers, constants become immediates, folded where both are known; the stack goes to its slots at sends, runtime calls and merge points (which start with every entry in its slot). Before an instruction that may send, everything below its operands is written back (unboxed Floats stay: its slow path boxes and reloads them around the send), so its slow path stores only the operands. An innermost loop that makes no closures, Arrays or `thisContext` keeps its most used temps (up to 3, each used more often than the loop sends) in x26–x28 too, stored through to their slots and reloaded after every call out of it (sends, slow paths). Layout: checked entry, unchecked entry, frame code, the bytecodes in pc order (block bodies with their entries), slow paths, resumption stubs, the literal pool, the `JitMethod` header (`adr` reaches it).

- *Sends*: the receiver in x0, receiver and arguments in their slots, `add x20` to the callee's fp, `ldr x9` the site's class from the pool, `bl` the site's target, `sub x20` after; the result comes back in x0. The target is the miss stub while unlinked; a compiled method's checked entry when monomorphic (its class check against x9: tag test, class word, compare; immediates by tag out of line); a `BaselinePic` of up to 6 classes, each branching to its target's unchecked entry; or, megamorphic, the megamorphic stub (x9 then holds the selector; a 4096-entry table probed in machine code). The miss stub calls `JitBaselineRuntime>>miss:receiver:ret:`, which looks the send up (the interpreter's global cache), compiles the target at the threshold, links or relinks the site (code patched under the W^X toggle) and jumps to the target; it leaves to the interpreter for `doesNotUnderstand:` and uncompiled targets. Young classes are cached too (their words become young roots). Method dictionary changes (`flushMethodCache`, `flushCacheFor:`), become and dead code unlink every (or every such) site. Super sends link once to the unchecked entry. Each site's state is its type feedback: `JitBaselineRuntime>>feedbackSitesOf:` and friends (pc, selector, state, receiver class and target per case), `CompiledMethod>>jitSendSites` in the image.
- *`perform:`* (Cog's `genPrimitivePerform`): `perform:` up to `perform:with:with:with:with:` and `perform:withArguments:` (an Array of up to 2) are compiled; their primitive probes the megamorphic table with the receiver's class and the selector, checks the entry's fourth word (the selector's argument count; -1 for a perform method: the interpreter does `perform:` of `perform:`), moves the arguments down over the selector and branches to the target's unchecked entry. A miss calls `performMiss:receiver:ret:info:`, which fills the table and enters the target, answers that the primitive failed (the method's body runs) or leaves as `miss:` does. The send of a callee entered so cannot be executed again: until its frame exists the runtime takes its sender as past the send (`setTop:ret:fp:argc:`), and a full stack is caught before the arguments move.
- *Frames*: the callee compares its fp against the JitState's stack limit (0 while an interrupt is pending: the one compare is also the interrupt check; `entrySlow:ret:callee:` takes the interrupt with the callee's frame pushed, popped again if no process switched), pushes the native record (x29, x30) and its Frame with two `stp`s and a `str` (code, closure and ctx nil, fp, pc and sp 0), x21 := the receiver, nil into its temps; a return pops both after one check (a married frame, or frame 0, which `run:at:` marries, takes the slow path). A Frame's method, pc, sp, ip and lits are lazy: the runtime makes a suspended frame canonical from the return address in its callee's native record (`canonicalizeBelow:`, the method's return map: return offset, pc, depth, argc, length, pushes; frame f's record is at `baseRecord − 16·(f − baseFrame)`), top down, stopping at the first frame that already is (a zero pc marks a frame pushed since). Every runtime entry that may collect, flush or leave does that first (`JitRuntime>>sync:`, the exit stub).
- *Quick methods* (^ivar, ^self, ^constant, ^literal, setters) run without a frame; with an interrupt pending they take the frame's path (sends are safepoints). *Primitives* run before the frame: in machine code for `basicNew`, `basicNew:` (eden bump allocation with the identity hash generator inline), `==`, `class`, closure `value`, SmallInteger and Float arithmetic and comparisons, SmallInteger `quo: rem: // \\`, `sqrt`, `truncated`, `charValue`, `Character value:`, `identityHash`, `at: at:put: basicSize` (pointers without fixed fields, 32-bit words, bytes), String `at:` and `at:put:` (Characters in bytes and 32-bit words), `uint32At:` and `uint32At:put:` of bytes; the others through their C function (`prim:fp:fn:info:`; leaf ones without canonicalizing). Failure continues into the frame and the body.
- *Inline at send sites*: SmallInteger `+ - * // \\ bitAnd: bitOr: bitShift:` and comparisons (tag checks only for operands not known, immediates, overflow branches), compare and branch fused with the conditional jump (a loop's bottom is one branch back to its head, where loops check for interrupts), jumps threaded into a conditional jump on the value just pushed (`and:`, `or:`). Floats: an operation with an operand that surely is a Float (an unboxed value, a Float constant, a temp whose unboxed value is known in the basic block) decodes the other (SmallFloat64, BoxedFloat64, SmallInteger) and leaves its result unboxed in a d register for the next one; other operations try SmallIntegers first, Floats out of line (SmallFloat64s straight through, the same temp twice decoded once); boxing (a SmallFloat64, else a BoxedFloat64 from the runtime) happens when a value goes to memory or a send. `== ~~ class` never send, nor do `isNil notNil` while only UndefinedObject and ProtoObject define them (a heap scan; another definition drops all code); `at: at:put:` inline for Arrays, out of line for Strings, Symbols and ByteArrays (`size` is sent: classes define their own, and Arrays answer it from the primitive in machine code); `value value: value:value:` check the closure's class and argument count and call the block stub, which finds the block's entry in a (home method, startpc) cache. Closures are allocated in eden, and with the first a frame makes, its Context (the frame married; eden full: the runtime makes them); Arrays (`0x94`) are runtime calls; outer temps inline; the store barrier's fast path inline (the remember stub saves the registers).
- *Non-local returns* leave to the interpreter.
- *Contexts*: `thisContext` calls the runtime, which marries the frame. 0x81 of `sender`, `pc` or `stackp` (Context's methods) loads the field unless the receiver's `sender` is a SmallInteger, a married Context: then the runtime answers it from the frame (`contextField:`; if that flushed, the interpreter executes it again). 0x88 is 0x85 with that check too: a married receiver leaves to the interpreter.
- Resumption points: method and block starts (an interrupt check out of line), loop heads, send continuations (a stub loads the result from its slot) unless unboxed values are live there. Exits go through the runtime so that the frames below become canonical.
- Flags (each switches one optimization off, for the ablations): `ic` (inline caches: every send looks up in the runtime), `pic`, `mega`, `regs` (every push to its slot), `arith`, `fuse` (compare and branch, jump threading), `float`, `access`, `prims`, `blocks`, `quick`, `barrier`, and `notes`.

## Optimizing tier

`--jit opt` (`OptBuilder`, `OptPasses`, `OptRegalloc`, `OptCodegen`, `OptRuntime`, `JitFeedback`; Lowtalk in `VM-Jit`). Baseline code is the lower tier; hot methods, blocks and loops are compiled again from their bytecodes with type feedback, inlining and speculation, and deoptimize to frames when a speculation fails.

**Tiering.** In this mode baseline code counts, per method (identity hash), method and block entries and backward jumps (`emitTierUp:depth:loop:`, a decrement of a word in the VM's data). At zero it stores pc and sp and calls the tier-up stub (x0 the frame, x1 whether at a backward jump); `OptRuntime>>tierUp:loop:` answers where the frame continues: the method's optimized code at its start, a block's unit, or a loop's unit (on-stack replacement at the loop head). Units are compiled once per method, per block (method, startpc) and per loop (method, block, loop head); a loop has a plain unit and up to 16 variants, each for one signature: a 32-bit hash of the code of the closures other frames made that the frame holds and of where they are (Inlining; `closureSignatureOf:`). A frame enters the variant of its signature (a new one while the loop has fewer than 16 and none that failed to compile, and there are fewer than 2048 variants in all: after that loops use their plain unit until the code cache is flushed); without one, or if it failed, the plain unit, which inlines no such closures. A failed compilation is remembered. Methods whose hashes meet share a count: it starts over at every tier-up, whatever the outcome. A method's optimized code is found by the activations through the method caches (`best:`) and installed over its baseline code's unchecked entry: a `b` to an entry that builds the frame as baseline code builds it (`JitBaselineRuntime>>redirect:to:`, undone on invalidation; not for quick methods and primitives); a block's unit is what the block stub enters from then on (its cache is cleared). `--jit-opt N` sets the count (default 1000), `--jit-flags eager` makes it 1. Frames resumed after a process switch (Contexts married to new frames) enter loop units too; if their code makes closures, the temps the closures reach stay in the frame (a closure may change them through the Context).

**Calls between the tiers.** Optimized code calls as baseline code does: receiver and arguments in their slots, the receiver in x0, x20 the callee's fp, `bl`, the result back in x0. A method it knows (the receiver's class known or guarded) it calls at its baseline code's unchecked entry (a primitive's machine code first; optimized code through the redirection), a closure it did not make through the block stub (after its argument count), anything else through an inline cache of its own, which `JitBaselineRuntime>>miss:receiver:ret:` links as baseline code's (monomorphic, polymorphic, megamorphic; unlinked with them). What baseline code leaves to the interpreter for (`doesNotUnderstand:`, a method not compiled yet; a `perform:` the machine code does not do) the miss handler sends through the runtime (`OptRuntime>>sendFrom:ret:`), as the entry stub's slow path does for an optimized caller when the stack is full; the stubs continue where it answers (the callee's entry, its frame pushed, or a `ret`: the result is in the receiver's slot). Callees build their frames (optimized code's entry from such calls builds it as baseline code does), so an optimized frame suspended in a call is lazy too: its return map (return offset, safepoint, argument count) gives `canonicalizeBelow:` and `setTop:ret:mode:` its pc (bytecode size plus the safepoint) and sp. Optimized code answers in x0 and keeps x23–x25 (baseline code's nil, true, false; reloaded after runtime calls). A C primitive that commits its result without switching processes returns into optimized code (the interpreter cannot continue its frame).

**Type feedback** (`JitFeedback`): per (method, bytecode pc) up to 4 receiver classes with counts, `FB_MEGA` beyond, and profile bits: Float operand, non-number operand, overflow, and why optimized code deoptimized there (class guard, arithmetic guard, bounds check, other). It does not depend on the compiler that collects it: baseline code reports every receiver class its inline caches miss on (`noteSend:pc:class:`) and, without a call, sets a byte per site when an inline Float path runs (`floatBitAddressFor:pc:`); deoptimization reports what failed (an arithmetic guard looks at the operands, a class guard at the receiver, a superinstruction's too). What baseline code takes inline without a send gives no feedback; the optimizer reads that as the inline case: `at: at:put: size` as Arrays (a String, which baseline code reads out of line, deoptimizes once, then has its case in the type switch), `value value: value:value:` as BlockClosures (both guarded), arithmetic as SmallIntegers; `isNil notNil` are comparisons with nil while no class but UndefinedObject and ProtoObject defines them.

**IR** (`OptIR`): nodes in fixed arrays (operation, representation oop or double, type: SmallInteger with a range, Float, Boolean, nil, Character, a class), blocks with predecessor edges, frame states (per activation: method, closure, receiver, pc, slot values, chained to the caller's) for every guard and safepoint, inlined activations. `OptBuilder` builds SSA directly from the bytecodes (Braun et al., Simple and Efficient Construction of Static Single Assignment Form, CC 2013), one variable per frame slot of every activation; arguments are never phis, nor are temps that neither a loop nor a closure of their activation (which may be inlined into the loop) stores. A frame state names nil for a temp that no bytecode from its pc on reads before storing it (`BytecodeAnalysis>>analyzeLiveness`, a backward analysis of each method's and block's slots 0–63): such temps make no phis and keep no values alive, and a frame rebuilt from optimized code has nil in them (Smalltalk looking into it sees nil there). Always named: arguments, slots from 64 on, every slot an outer-temp instruction of the method names, all temps of a method with a primitive or `thisContext`, temps kept in the frame. A bytecode the builder decodes that reads a temp the analysis has dead prints `samaltak: liveness mismatch` and gives up the compilation.

**Inlining.** `perform:` of a constant selector the receiver's class understands is a send of it, inlined or called as any other; its arguments go a slot down, frame states at it keep the `perform:`'s slots, and deoptimization before its call puts the selector back (`SI_PERFORMED`). Other `perform:`s call the perform methods' machine code. A send is inlined for the class the receiver is known to have, or speculated from feedback: one class behind a guard, up to four behind a type switch (anything else deoptimizes; at an arithmetic site that saw Floats, which baseline code's inline paths report no class for, it is sent); a mega site, one that deoptimized for a class, and sends without feedback are inline caches; a method with baseline code that is not inlined is called at its unchecked entry (Calls between the tiers). Methods up to 200 bytecodes, 3000 in all, 8 deep, a recursive one once. Blocks evaluated by an inlined `value…` send are inlined into the activation that made them; their closures are never made: frame states describe them (sunk), deoptimization makes them, marrying the frames they refer to. A closure that escapes (stored, passed, answered) makes the compilation start over without inlining the method that made it. A loop's unit (on-stack replacement) inlines the closures its frame made before the loop, in the temps that hold them: guarded by class, startpc and outerContext (the frame's Context), else deoptimize. A loop's variant inlines too the closures other frames made (a block passed to `do:`, `inject:into:`) that the frame holds (its first 64 slots), or that such a closure's outer temps hold (the first 32 of each Context out from it): guarded by class, startpc and their outerContext's method; their outer temps and `self` through the closure. Not those with `^`, `thisContext` or more than 200 bytecodes; anything else the compilation cannot do in one makes it start over calling that closure. `^` in an inlined block is a jump to the home activation's return; in a block's unit it deoptimizes, and the unit is not optimized again.

**Primitives and speculation.** SmallInteger `+ - * / < > <= >= = ~= // \\ quo: rem: bitAnd: bitOr: bitXor: bitShift:` with tag guards and overflow checks (`/` exact: a remainder deoptimizes, and the site sends it from then on) (Boolean results branch directly, no frame state); Float `+ - * / < > <= >= = ~= sqrt` on doubles (SmallFloat64, BoxedFloat64 or SmallInteger operands decoded, the result encoded; out of SmallFloat64's range, a zero divisor: deoptimize; a box unboxed again is its double, and a box only frame states name is not made (they name the double); a site whose feedback shows Floats and never two SmallIntegers has no SmallInteger path, two SmallIntegers deoptimize; one without Float feedback of its own in a method whose arithmetic saw Floats has both paths, unless it reported receivers that are not numbers); `at: at:put: size basicSize` with bounds checks for pointer, byte and string objects; `basicNew basicNew:` of pointer objects in eden (header, class, nil fields inline; the send when eden or the allocation sample's limit is reached); `== ~~ class`, `Character value`, `Character value:`; `value value: value:value:` of a closure the IR does not know: the block stub (its unit if it has one). Interrupt checks at method entries and backward jumps; the write barrier inline, left out for stores of immediates, nil, true and false; immutability checked once per object and block.

**Passes** (`OptPasses`): unreachable blocks, trivial phis, phis of SmallIntegers (a loop's counter, a running sum) typed as such and their guards dropped, phis of SmallFloat64s typed as such and carried on doubles, their boxes left to the stores and returns after the loop (below), global value numbering over the dominator tree (guards, arithmetic, comparisons, Float conversions and doubles, constants; field loads within a block with no store or safepoint between), critical edges split, guards hoisted out of loops, unused pure nodes, reverse postorder. A guard that every turn of a loop passes, of a value from before the loop, runs once where the loop is entered (`hoist`; loops with one edge in); it deoptimizes to the loop's head as the loop is entered (the frame state the builder made for the head, its phis what they take on entry), and if it fails its send is marked: there the guard stays in the loop from then on.

**Registers** (`OptRegalloc`): linear scan (Poletto and Sarkar) over one interval per value: x0–x13, x26–x28, doubles d16–d31; a value without a register lives in its slot (the interval ending last is spilled), and a value live across a safepoint also has a home slot in the frame (an argument's is its own slot, a guard's result its input's; a double's is a raw slot), stored at its definition, or on the slow path of the interrupt checks if they are the only safepoints it crosses, and reloaded after the safepoint; constants are rematerialized.

**Unboxed Floats in loops.** A phi of SmallFloat64s is typed as one: every operand a box, a Float constant, a value of that class or such a phi; in a loop's unit also a frame slot that held one when the unit was compiled, guarded where the unit is entered (failing, the interpreter continues at the loop's head). It has a twin on doubles, a phi of the doubles of those boxes, of the constants and of those phis' twins (any other operand is decoded where it flows in, no check), and what unboxed the phi reads the twin: a running sum stays on doubles around its loop, across nested loops and where branches meet. A phi whose box nothing needs is gone. Frame states name its twin (deoptimization boxes it). A store into a field or an element, or a return (not a block's `^`), that runs no more often than the phi (after the loop, for a loop's own phi) boxes the twin itself, right before, with its own frame state: out of SmallFloat64's range it deoptimizes, the interpreter stores or returns, and that site reads a box from then on. A box in a loop that only such stores and returns after the loop read is made there instead, the same way. Anything else that reads the phi or the box needs it boxed (a send, a store in the loop, a guard, arithmetic with a SmallInteger path, an activation's receiver, a phi that is not of SmallFloat64s), as does every phi and box that flows into one that is: these are boxed beside the chain of doubles. A loop head's phi in a loop's unit whose frame held another number there (a SmallInteger, a BoxedFloat64) gets a twin for the loop's arithmetic only, if nothing but boxes, Float constants and itself flows into it around the loop: the entry unboxes the frame's value once, under a guard, and the boxed phi stays, its boxes made every time around. Across the loop's sends and interrupt checks a twin is in its raw slot; a compilation its twins make fail is done again without them. Float constants are loaded as doubles (`fmov` immediates where they encode). Phi moves are sequentialized (cycles through a scratch register; doubles through d0, a raw slot to a raw slot through d1).

**Code and frames** (`OptCodegen`). An optimized frame is a frame: x19–x22 as in the lower tier, the root activation's arguments in their slots, then home slots, then raw slots (the IEEE bits of doubles, from the header's `rawBase`, after the frame's temps: the collector, its verifier and a widowed Context skip them) and the outgoing receiver and arguments; its `pc` is the bytecode size plus a safepoint number (stored at its own safepoints, derived from the return map in calls). Method and block units start with the entry of calls as baseline code makes them, then the prologue for callers that pushed the frame; a method takes its receiver from x0, where calls bring it (the prologue loads it there). Blocks go in reverse postorder, but a loop's back edge right after the comparison that branches to it (a turn takes one branch). nil, true and false come from x23–x25. The generator knows which registers hold which slots, from what it emitted since the last label (a slot load or store makes its register hold the slot, other writes, calls and jumps undo that): such a slot is not loaded (moved if another register holds it) nor stored again. Out-of-line paths after the code: guard failures, interrupt checks, store barriers, deoptimization after a call, resumption after a call (the interpreter returned into the frame: the result from its slot), the stack check, the bottom frame's return. The header holds the safepoint table, the deoptimization records (kind, the send, per activation method, closure, receiver, pc and the location of every slot: register, slot, constant, sunk closure, a double's d register or raw slot), the dependencies, the inline caches and the return map; an oop pool after the code (pc-relative loads, GC roots), then the inline caches' literals. The listing (`machineCodeFor: #opt`) shows the root method's bytecodes and the inlined activations' pcs.

**Deoptimization** (`OptRuntime`). A failed guard jumps to a stub that saves the registers; the record rebuilds the activations as frames (a double that is a SmallFloat64 becomes one, others one BoxedFloat64 per location once the frames are written, and the closures never made are made), the interpreter continues the innermost one, and the site's feedback learns what failed. A failure the feedback had not reported, or one in code compiled before the site's feedback last changed, invalidates the code at once (it compiles differently next time), so does the ninth deoptimization; a site that fails again in code compiled with what it reports now is marked: no speculation there next time; a unit is compiled at most 32 times. `materializeAll` (process switches, Smalltalk looking into an optimized frame) turns an optimized frame into a Context per activation; the interpreter returning into an optimized frame resumes it at its safepoint. Invalidation (lazy): a method added or removed for a selector the code inlined or speculated on (`flushCacheForSelector:`), become of a method: the code is marked dead, frames running it deoptimize when control comes back to them (a check after every call), calls into it go to the lower tier. Switching the mode away from `opt` makes every optimized frame Contexts first.

**Contexts.** Methods with a marker primitive (`on:do:`, `ensure:`, `ifCurtailed:`) are not optimized, so the frames the exception code reads and writes through their Contexts are plain; methods with `thisContext` or Context's mediated forms (0x81 of fields 0–2, 0x88) neither, and none of these is inlined. An optimized frame is married only when it is entered married (a loop's unit; its return widows it). Smalltalk does not look into one: marrying it (the sender of a married Context) or reading a married one's pc, stackp or slots flushes the frames instead. A suspended frame cannot be deoptimized in place without moving every frame above it. Sends to Contexts link and call like any other.

**Stress.** `--jit-flags eager` optimizes at the first count; `deopt` makes optimized code take every 37th slow path it passes (guards, interrupt checks, returns from calls) and deoptimize there, without feedback. `make test-jit` runs the image's tests under `--jit opt` with eager and with eager,deopt; `vm/tests/run.sh` the mini kernel's under both (with the GC stress) and the default thresholds; `JitOptRuntimeTest` covers deoptimization of a failed speculation (and none where nothing was speculated: `perform:`, `doesNotUnderstand:`, SmallIntegers beside Floats, BoxedFloat64s), invalidation of inlined code while it runs, closures that store temps across loops, closures a loop's unit inlines from its frame, calls into machine code (no sends through the runtime: `optRuntimeSends`), process primitives that switch no process, `perform:` of a constant (inlined), `at:` of a String argument (inline after one deoptimization), a count shared with a method that failed to compile, a loop's values across interrupt checks where Processes switch and the collector runs, Float loops on doubles (across those interrupt checks; a loop's unit entered with a SmallInteger, a Fraction or nil, and one compiled for a SmallFloat64 entered with one, a SmallInteger or a BoxedFloat64; a loop that sends; more running Floats than d registers; running Floats without boxes in their loops: boxed where they are returned or stored after it, by the interpreter out of SmallFloat64's range; across nested loops, a conditional's phi and a swap; where a guard fails in the loop; one the loop sends, boxed there), deoptimization with dead temps (straight code, branches, loops, nested Float loops, blocks, a loop's unit) and a frame made a Context with nil in its dead temps, the stress, the listing.

**Flags** (`--jit-flags`, all on by default): `inline` (methods), `blocks` (closures), `prims`, `unbox` (Floats on doubles), `calls` (direct and block calls), `alloc`, `gvn`, `hoist`, `live` (frame states name only the temps still read; off: every temp); `eager` and `deopt` are off.

Not done: loop-invariant code motion other than class and SmallInteger guards' (an argument's unboxing stays in the loop, check and all: NBody's `dt`), range analysis and bounds-check elimination, escape analysis beyond closures, unboxed Floats across calls, in fields and in elements (a store boxes, a load unboxes under a check: NBody's `advance`), in a loop's variable that starts as a SmallInteger (`sum := 0`: in the method's unit not a phi of SmallFloat64s, boxed every time around) or that arithmetic with a SmallInteger path reads (SpectralNorm's `vBv / vv`: its boxes stay in the loop), SmallInteger phis for counters whose arithmetic has a Float path too (Primitives and speculation: Float arithmetic that reads Mandelbrot's `x` converts it under a check), inlining of closures made elsewhere other than in a loop's variant (a method's unit calls a block passed in through the block stub).

## Machine code

Package `VM-Jit` (layer 0), shared by both compilers:

- **`JitAssembler`**: what the code generators connect to (`asm`), an arch interface (docs/lowtalk.md, CPUs): `Arm64Assembler` on arm64, `Amd64Assembler` on x86-64 (below). Both take the messages listed next; `asm isX64` folds where a generator emits code of x86's own.
- **`Arm64Assembler`** (Lowtalk module, translated with the JIT). `asm beginAt: start limit: end`, one message per instruction with operands in assembly order, `asm finish` (an `ASM_*` error code; the first error sticks). Registers, conditions, shifts, extends and barriers are class variables of `Arm64Module` (subclass it to use them): `X0`–`X30`, `XZR`, `SP`, `W0`–`W30`, `WZR`, `WSP`, `D0`–`D31`, `COND_EQ`…, `SHIFT_LSL`…, `EXT_SXTW`…, `BARRIER_ISH`…; the width (W/X) comes from the destination register, FP forms from D registers (`ldr: D0 base: X1 offset: 8`). Selectors: `add:with:imm:` (also `adds sub subs`, `cmp:imm:`, `cmn:imm:`; lsl #12 and negative immediates chosen automatically), `add:with:with:` `…shift:amount:` `…extend:amount:`, `neg:with:`; `and orr eor ands bic` `:with:imm:` (bitmask immediates) and `:with:with:[shift:amount:]` (also `orn eon bics tst mvn`); `mov:with:`, `mov:imm:` (shortest movz/movn/movk or orr), `mov:imm64:` (fixed four instructions, patchable), `movz/movk/movn:imm:shift:`; `lsl lsr asr ror` `:with:imm:` and `:with:with:`; `mul madd:…add: msub:…sub: smulh umulh sdiv udiv clz`; `csel csinc csinv csneg` `:with:with:cond:`, `cset:cond: csetm:cond: cinc cinv cneg:with:cond:`; `ubfx sbfx ubfiz sbfiz bfi bfxil` `:with:lsb:width:`, `ubfm sbfm bfm`, `sxtb sxth sxtw uxtb uxth`; `ldr str ldrb strb ldrh strh ldrsb ldrsh ldrsw` `:base:offset:` (scaled, else unscaled) `:base:preIndex:` `:base:postIndex:` `:base:index:[extend:shift:]`, `ldur stur …`, `ldp stp` `:with:base:offset:/preIndex:/postIndex:`, `ldr:label:`; `adr:label: adrp:label:`; `b: bl: b:if: cbz:to: cbnz:to: tbz:bit:to: tbnz:bit:to: br: blr: ret ret:`; `nop brk: dmb: dsb: isb`; `fmov:with: fmov:imm: fadd fsub fmul fdiv` `:with:with:`, `fsqrt fneg fabs frintm frintp frintz frintn scvtf ucvtf fcvtzs` `:with:`, `fcmp:with: fcmpZero: fcsel:with:with:cond:`. Labels: `newLabel`, `bind:`, `labelAt: anAddress`; forward branches are patched at `bind:`; `labelsBound` counts the labels bound, `hasBranchesTo:` tells whether an unbound label has branches to it. Encoders: `logicalImmediate:width:`, `fmovImmediate:` (-1 if not encodable). Patching: `patchBranchAt:to:`, `branchTargetAt:`, `patchMov64At:value:`, `mov64At:`. Notes for annotated disassembly, recorded only after `recordNotes: true`: `comment:`, `comment:with:`, `bytecode:`. With constant operands an instruction is one store of a constant word and a limit check; emission runs at about 3·10^8 instructions/s (`Tests-VM/JitSample` with the argument `bench`, cc -O2, M2 Max).
- **`CodeCache`** (Lowtalk module): `openWithSize:` (one `MAP_JIT` mapping), `allocate:`, `keep` (what is allocated survives flushes), `flush`, `beginWriting`, `endWritingFrom:size:` (`pthread_jit_write_protect_np`, `sys_icache_invalidate`, bound in the library `DarwinJit`), `endWriting`, `invalidate:size:`. Code is called by casting its address: `(self cCoerce: entry to: 'int64_t (*)(int64_t)') call: 42`.
- **`Arm64Disassembler`** (image): `textFor:at:` prints as LLVM's objdump does; `listingOfWords:at:annotations:` prints a listing with `Arm64CodeAnnotations` (bytecode headers, comments, labels for branch targets, symbol names for calls).
- **`Amd64Disassembler`** (image): `textFor:at:` prints as GNU objdump `-M intel` does, `instructionsOf:at:` decodes one instruction after the other; `listingOfBytes:at:annotations:` prints a listing as `Arm64Disassembler`'s.
- **`JitRuntime`**, **`BytecodeAnalysis`** (VMCoreModules), **`JitCompiler`**, **`JitStubs`** (Arm64Modules), **`JitPrimitives`** (`jitParameters`: `Smalltalk vm jitParameters`, `jitMode:`; `jitCode`): the shared runtime, part of the VM.

- **`Amd64Assembler`** (Lowtalk module, x86-64): the same messages, each emitted as x86-64 (x86-64, below), plus `push: pop: callC: loadReturnAddress: muls:with:with: cmp:withStateWordAt: cmpStateWordAt:imm: decrement32At: picCaseX64:classAt:target:` for code of x86's own, and `effectAt:` (what an instruction it emitted does to what registers hold); labels are fixups of 32-bit displacements, `patchBranchAt:to:` rewrites one (a call site's: 4 bytes before its return address), `mov:imm64:` is a movabs (its constant 2 bytes in).

The simulator runs the VM without the JIT: machine code does not run there (`CodeCache>>canRunCode`), so `JitRuntime>>start` turns it off, whatever `--jit` says.

Tests (`Tests-VM`): encodings against the system assembler's (`Arm64Reference` and `Amd64Reference`, generated by `tools/arm64-reference.py` and `tools/amd64-reference.py`), simulated and compiled with cc; disassembly against objdump; x86's branches, patching, words in memory and what its instructions do to what registers hold (`Amd64AssemblerTest`); `JitTest` runs `JitSample` natively; `JitRuntimeTest` covers on-stack replacement, redefinition and become while machine code runs, literals in the code, process switches, deep recursion, `perform:` (argument counts, failures, kinds of target, many selectors at one site, interrupts at its targets' entries), code cache flushes and the listing under `baseline`, `JitOptRuntimeTest` the same under `opt`; `JitBaselineTest` the baseline's inline caches through their states, relinking, unboxed Floats when Smalltalk runs in a slow path, Floats' slow paths (squares, every operand kind), loops' bottoms and loops entered by a threaded jump, non-local returns, allocation, the primitives in machine code against their C functions and every ablation flag. `vm/tests/run.sh` runs the mini kernel's tests also under `--jit baseline` and under `--jit opt` (eager; eager,deopt) with `--jit-threshold 0` (with the GC stress) and the default thresholds; `make test-jit` the image's tests under `none`, under `baseline` and under `opt` (eager; eager,deopt) with `--jit-threshold 0`, Tests-Kernel also under `opt` with a 1 MB cache (2 MB on x86-64, whose code is a third bigger) that keeps notes (it is flushed again and again).

## x86-64

The code generators are the same on both CPUs: they emit arm64's instructions with arm64's registers, and on x86-64 `Amd64Assembler` emits each as the x86-64 instructions that do what it does (an `add` with three registers a `lea`, a `tbz` a `test` or `bt` and a `jcc`, `ldp` two `mov`s, `csel` a `cmov`, ...). Where x86 has a better sequence or no counterpart, the generator branches on `asm isX64`, which the translator folds per CPU (docs/lowtalk.md, CPUs), so the arm64 build compiles the same C as before the port. `tools/lowering-check.sh` runs random programs of these instructions as x86-64 and, under `qemu-aarch64`, as arm64: they must leave the same registers and memory.

**Registers.** x0–x5 are rdi rsi rdx rcx r8 r9 (C's argument registers: the runtime's arguments are where SysV wants them), x9 rax, x10 r14, x11 r15, x16 r10, x17 r12, x19 rbp, x20 rbx, x21 r13, d0–d15 xmm0–xmm15; r11 is the assembler's scratch, rsp is sp. x22 has no register: the JitState is a global, so its words are `[rip + disp32]` (the code cache is in the VM's BSS, within 2 GB); x23–x25 (nil, true, false) are its words, read where they are used, and their reloads after calls are nothing. Every other arm64 register (x6–x8, x12–x15, x18, x26–x28) is a word of `asmRegs`, a register file in memory: correct, slower; the code generators keep out of them where it matters. So baseline code's operand-stack registers are x0–x5, it has no loop temps in registers, and optimized code allocates x0–x5, x9 and x21 (r13: optimized code does not keep the receiver there) and d2–d15; its scratch registers are x10, x11, x16, x17.

**Flags.** Most x86 instructions write the flags, arm64's only those that say so. The assembler tracks the kind of the last instruction that set them (subtract: the carry is inverted; add; logical; floating point compare: an unordered result sets the parity flag, so EQ, NE, MI, LS and their opposites take two tests; multiply: overflow; `bt`, which tests one bit beyond a 32-bit immediate's reach: the bit in the carry, for EQ and NE), across labels too (each branch brings its kind, a label merges them), and fails to compile (`ASM_ERR_FLAGS`) code that reads flags its own x86 code destroyed, rather than run it wrong. `muls:with:with:` multiplies with the overflow in the flags (`imul`, `jo`) where arm64 compares `smulh`.

**Frames and calls.** `call` pushes the return address: that word is an activation's native record (8 bytes, where arm64's x29/x30 pair is 16; `canonicalizeBelow:` reads it at `baseRecord − 8·(f − baseFrame)`), and `stp`/`ldp`/`str`/`ldr` of x29 or x30 with sp are nothing. The prologue is 12 bytes (`JIT_PROLOGUE_BYTES_X64`). A stub that calls C aligns the native stack to 16 (machine code keeps it 8-aligned), keeps xmm8–xmm15 (baseline code's unboxed Floats; SysV saves no xmm register) and moves the result from rax to x0 (`callC:`); `jit_enter` saves SysV's callee-saved registers and asmRegs' x26–x28. Call sites are `call rel32`, their displacement the site (`siteBl`); a polymorphic inline cache's cases are 14 bytes each (`cmp r10, [rip + class]`, `jne`, `jmp`), a redirected unchecked entry starts with a 5-byte `jmp` over its stack check (`cmp rbx, [rip + limit]`, its first byte 16r48 and the 4 bytes after it kept in `entryWord`). The stack, interrupt and tier-up checks compare or decrement the JitState's words in memory.

**What registers hold.** `OptCodegen>>catchUp` decodes the x86 code it emitted as it does arm64's: `Amd64Assembler>>effectAt:` tells what an instruction does (a 64-bit load or store of an `rbx` slot, a move, a write; calls, jumps, pushes and other stores into the frame forget all; a short jump forward over the assembler's own code counts as what that code does), in arm64's registers; an instruction it does not know ends what is known.

Not done on x86: loop temps in registers (no registers to spare), BMI2's flag-free shifts. Speed: docs/benchmarks.md (Are We Fast Yet, x86-64).
